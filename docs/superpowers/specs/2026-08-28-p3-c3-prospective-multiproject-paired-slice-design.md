## 1. Scientific objective

The local ordinal-8 chain is complete and must not be enlarged. On one
NumPy subject, four frozen semantic–syntactic pairs produced:

- semantic pair-level kill 4/4;
- syntactic pair-level kill 3/4;
- `D_subject = 0.25`;
- normalized-patch exact overlap 0/4;
- mutant-tree exact overlap 0/4.

Those facts are local paired execution and construct-identity evidence.
They cannot identify project-clustered sampling uncertainty because
`n_projects = 1`. The next scientific act is therefore not another
ordinal-8 supplement. It is a prospective search for two additional
paired-evidence-complete subjects from two repositories/projects that are
distinct from each other and from NumPy, so that the retained structure
becomes a 3-project pilot.

A 3-project pilot is the smallest cluster structure on which the frozen
RQ2 project-clustered interval is mathematically computable. It is not a
sufficient sample for C3, not a population effect, and not a stopping
rule based on significance.

## 4. Project identity

A project/repository is not a snapshot, not a subject, and not a
descriptor. `neutral_snapshot_id`, `controlled_subject_id`,
`source_archive_sha256`, `build_descriptor_sha256`, ecosystem, and
language family are not project keys.

The project-cluster key is the originating repository identity bound to
that `neutral_snapshot_id` by the P3 local project-cluster authority at
`data/p3_v3/phase3/inputs/project-cluster-authority-v1.json`. That file
is a P3 analysis input. It is created only after every frozen
`source_archive_sha256` and `normalized_source_tree_sha256` pair uniquely
matches one public upstream revision under P12-BRIDGE-SNAPSHOT-RULE-v2.
It does not extend bridge v1, does not modify the consumer lock, and does
not open the P12 eligible inventory.

The controller uses 19 originating repository identities as project
clusters. The manuscript may describe 18 program groups; those groups
are paper-only labels and are not project-cluster keys.

Slice A must bind the key from the validated local authority before any
successor site is opened. A user-supplied map is forbidden. Language,
ecosystem, and program labels are not fallback keys. Binding failure is
`IDENTITY_CONFLICT` and stops the slice.

Two subjects belong to the same project if and only if those bound
repository identities are equal. NumPy ordinal 8 is one project. Two
later subjects count as two of the two required new projects only when
their repository identities differ from each other and from NumPy. The
scientific terminal records
`project_cluster_authority_artifact_sha256` in addition to the existing
applicability `authority_artifact_sha256`. Stopping, successor identity,
pair budget, and failure rules in this design are unchanged.

If two ordinals from the same repository both reach
`PAIRED_EVIDENCE_COMPLETE`, both remain in the funnel. They are averaged
inside that project and do not satisfy the two-new-project stop by
themselves.

## 5. Stopping rule

Process ordinals in order 9 → 22 until one of the following holds.

A. Two subjects have `PAIRED_EVIDENCE_COMPLETE`, their project keys are
   distinct, and both differ from NumPy. Together with ordinal 8 this is
   the 3-project pilot.

B. Ordinals 9–22 are exhausted.

Finding two new projects is not a sufficient sample for C3. It only
moves project-clustered uncertainty from `UNIDENTIFIABLE` to
computable-but-unstable. Significance is not a stop rule. A favorable
`D_subject` is not a stop rule. Overlap counts are not a stop rule.

## 6. Per-subject pipeline

Each opened successor, in this exact order:

1. source identity;
2. existing-authority 10-slot applicability closure;
3. source-authorized contract freeze;
4. paired semantic/syntactic mutant construction;
5. original / semantic / syntactic controlled execution;
6. normalized-patch exact overlap;
7. mutant-tree exact overlap;
8. subject-level paired reduction.

Subject terminals:

| Terminal | Class | Slice action |
|---|---|---|
| `ALL_SLOTS_NOT_APPLICABLE` | scientific funnel | keep the subject; continue to the next ordinal |
| `SITE_ELIGIBLE_NO_AUTHORIZED_CONTRACT` | scientific funnel | keep the subject; continue |
| `PAIR_CONSTRUCTION_UNAVAILABLE` | scientific funnel | keep the subject; continue |
| `PAIRED_EVIDENCE_COMPLETE` | scientific success | keep the subject; continue only if the two-new-project stop is unmet |
| `INFRASTRUCTURE_FAILURE` | execution failure | do not label ineligible; do not skip; stop the slice |
| `IDENTITY_CONFLICT` | execution failure | do not label ineligible; do not skip; stop the slice |

The first three terminals remain in the funnel. They are not construct
absence and not kill failures. Resume after an execution failure is
undefined here and requires a later separate authorization.
`NO_SCIENTIFIC_RETRY` is the only retry policy in this design.

## 7. Pair budget

To stop subjects with more pairs from dominating:

- use the frozen slot-inventory canonical order for that
  `controlled_subject_id`;
- take every source-authorized semantic–syntactic pair, at most 4 pairs;
- if more than 4 exist, keep the first 4 in canonical order;
- if fewer than 4 exist, keep the actual count;
- `PAIRED_EVIDENCE_COMPLETE` requires at least 1 pair;
- pair count is not chosen from kill/survival, overlap, or run success;
- each pair uses its frozen 5 `E_CONTRACT` inputs;
- original cells must all pass before the corresponding mutant
  kill/survival is interpreted;
- every failed or unobserved cell remains in the execution funnel.

Ordinal 8 keeps its existing 4 pairs. They are not reselected.

## 8. Analysis units

For each subject:

```text
D_subject = semantic pair-level kill proportion
          − syntactic pair-level kill proportion
```

Rules:

- the primary reduction unit is the frozen pair, not the input cell;
- each subject has total weight 1;
- frozen pairs inside a subject are equally weighted;
- the 5 input cells are repeated measures that compose a pair verdict,
  not 5 independent experiments;
- if one project unexpectedly yields several subjects, average those
  `D_subject` values with equal subject weight to obtain `D_project`;
- the bootstrap cluster is the project;
- NumPy ordinal 8 is included, with its already observed
  `D_subject = 0.25`.

Reports must include, for every retained subject:

- pair-level contingency (both killed, semantic only, syntactic only,
  neither);
- `D_subject`;
- project-level aggregated difference;
- semantic and syntactic execution funnels;
- contract-family and mechanism coverage;
- normalized-patch and mutant-tree exact overlap.

Input cells must not be treated as independent samples. Sites are
structural disclosure only and are not project clusters.

## 9. Project-clustered uncertainty

| `n_projects` | Status |
|---|---|
| 1 | `UNIDENTIFIABLE` |
| 2 or 3 | mechanically computable after the bootstrap implementation is bound; the interval will be extremely unstable |

A 3-project pilot does not satisfy the C3 upgrade condition. Cell, pair,
or site bootstrap is forbidden as a substitute. Bootstrap replicates are
not new data. Significance is not a stop rule.

The governing plan requires project-clustered intervals and, for later
RQs, resampling or permuting entire projects. The production `src/p3_v3`
tree has no bound algorithm that implements that requirement for RQ2
paired differences. This design therefore records:

`BOOTSTRAP_IMPLEMENTATION_AUTHORITY_REQUIRED`

It does not invent a menu of algorithms, replicate counts, or interval
recipes. Slice E may compute an interval only after a later
authorization binds exactly one project-clustered implementation. Until
that binding exists, any 2- or 3-project numeric interval is unauthorized.
